## Purpose

Task **B4**: define the `.nbdb` Device DB container, and give it a deterministic host generator, an independent host validator and a firmware reader that all agree. The production corpus lives on SD; nothing here ships a corpus in flash.

## Relationship to the previous NearBy One NEXT `.nbdb` — no compatibility assumed

The previous project's source is **not available in this environment**. Only its reuse matrix survives, in `docs/application/provisioning-web-management.md` section 9, which describes `db_storage.c` and a browser-side preflight check but **not the file layout**.

So the container is defined from scratch and **does not assume wire compatibility** with the old file. The extension is reused because the product documents fix the name `devices.nbdb`; explicit `format_version` / `schema_version` / `reader_abi` fields mean an unrecognised file is rejected as `INCOMPATIBLE` rather than misread. If the old format is later recovered, a one-way converter can target `format_version = 1` without touching the reader. This is recorded in `docs/device-db-format.md` §1 rather than left implicit.

## Format summary

- Little-endian, byte-assembled (never `memcpy` of a struct), so struct layout is not part of the format.
- 128-byte header with **separate** `header_crc32` (bytes 0..119) and `body_crc32` (bytes 128..end): "header corrupt" is distinguishable from "body corrupt", and a damaged body cannot hide behind one whole-file checksum.
- Eight sections, each with offset **and** length: strings, provenance, identity rules, profiles (96B), fingerprints (40B), recipes (72B), index buckets (32B). A `StringRef` packs (offset, length) into one `u32`; strings are never copied by the reader.
- 16 MiB hard cap so a hostile size field cannot drive a large allocation.
- The index is a power-of-two bucket table that **never drops entries**: an overflowing bucket is flagged and its extras go to a contiguous overflow run. It is an accelerator only — the caller must confirm against the fingerprint record, and `device_db_index_lookup()` reports `may_be_incomplete` instead of "not found".

## Rules encoded in the format, not just in prose

- A profile marked `writable` must actually have a writable recipe.
- `WRITE_CONTROL` requires `USER_ACTION_REQUIRED` — a state-changing operation always needs explicit user action.
- Identity kinds that must never merge devices (BLE random address, Wi-Fi BSSID, IP, RSSI, SSID, model name, Matter VID/PID alone) may only be recorded as `UNSAFE`: they can be shown, never used to merge.

## Provenance gate

`tools/device_db/sources/source_manifest.json` declares each upstream source, license and reuse class. A profile whose only justification is `REFERENCE_ONLY` material is **rejected by the generator**, not shipped. `permitted_for_output` lets a license review revoke output without editing every profile. The fixture corpus cites only One-OS-authored material.

## Fixtures: test-only

`tests/fixtures/device_db/` holds the valid fixture plus **29** deliberately damaged variants, each a single named mutation with both CRCs recomputed — so each variant is rejected for the rule it breaks, not because a checksum happened to notice. Nothing under `tests/fixtures` is referenced by the firmware build; there is no fallback matcher in flash.

Fixture coverage: a known BLE beacon, a writable Zigbee plug, a deliberate **ambiguous** pair sharing one key, a **distinct** model that must not merge with the beacon, and an mDNS printer.

`device_db_python` (36 checks): generator determinism, provenance gate, recipe/policy/identity rules, string limits, validator accepts the fixture, rejects all 29 variants, and rejects **every prefix** of a valid file.

`device_db_format` (C reader): accepts the same fixture and decodes the expected profile/recipe/identity/index values, and rejects all 29 variants. The variant list is read from the generated manifest, so a missing variant fails instead of being skipped.

## Defects found and fixed while building this

1. A Python CRC-32 helper had an operator-precedence bug (`&` binds tighter than `^`), producing a wrong checksum.
2. `nbdb.py` originally wrote recipes/profiles with one long `struct` format; a format-string mismatch had already silently shifted fields. Both records are now written by **explicit offset**, matching the spec's offset table, which removes that whole class of bug.
3. The independent validator hashed the raw display key while the generator hashes the normalised form; the validator was wrong.
